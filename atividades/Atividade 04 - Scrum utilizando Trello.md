# Atividade PBL — Planejamento das Sprints no Trello

## Objetivo

Estruturar o projeto PBL no Trello utilizando conceitos de Scrum, organizando o **Product Backlog**, definindo **Sprint Goals**, planejando as próximas Sprints e tornando o trabalho da equipe visível.

## Organização

- Atividade em grupos do projeto PBL;
- Ferramenta: Trello;
- Não é necessário programar;
- O foco está no planejamento e na organização do trabalho do projeto.

---

# 1. Preparação do Quadro

Cada grupo deverá criar ou organizar um quadro Trello para o projeto.

Criem as seguintes listas:

- **Sprint**
- **Product Backlog**
- **Sprint Backlog**
- **Doing**
- **Review**
- **Done**

Também deverão:

- colocar o nome do projeto no quadro;
- adicionar todos os integrantes;
- definir quem exercerá inicialmente os papéis de **Product Owner** e **Scrum Master**.

## Uso das listas

### Sprint

A lista **Sprint** deverá conter cartões especiais representando as Sprints planejadas.

Exemplo:

- Sprint 1 — Compreender os usuários e as regras centrais;
- Sprint 2 — Representar a solução;
- Sprint 3 — Validar e revisar a proposta.

Esses cartões servem para registrar o **Sprint Goal** de cada Sprint.

### Product Backlog

Contém todos os itens conhecidos que poderão ser realizados ao longo do projeto.

### Sprint Backlog

Contém apenas os itens selecionados para a Sprint que estiver sendo executada.

### Doing

Contém os itens atualmente em execução.

### Review

Contém os itens concluídos pela equipe, mas que ainda precisam ser revisados ou validados.

### Done

Contém os itens considerados finalizados e aceitos.

---

# 2. Definição das Etiquetas de Sprint

Criem etiquetas no Trello para identificar a qual Sprint cada cartão pertence.

Sugestão:

- **Sprint 1**
- **Sprint 2**
- **Sprint 3**

Todos os cartões planejados para uma Sprint deverão receber a etiqueta correspondente.

A etiqueta indicará **quando o item está previsto para ser realizado**, enquanto a lista indicará **em qual estado do fluxo de trabalho o item se encontra**.

Exemplo:

Um cartão com a etiqueta **Sprint 2** pode estar no **Product Backlog** enquanto ainda não chegou sua Sprint.

Quando a Sprint 2 começar, ele poderá ser movido para:

**Sprint Backlog → Doing → Review → Done**

---

# 3. Construção do Product Backlog

O grupo deverá transformar o que já sabe sobre o projeto em cartões.

Criem entre **12 e 20 itens**.

Os cartões podem representar:

- necessidades do usuário;
- funcionalidades;
- requisitos ainda a esclarecer;
- protótipos;
- modelos;
- validações;
- documentação;
- investigação de regras do domínio.

## Exemplos de cartões

- identificar os perfis de usuários;
- definir dados necessários para cadastro;
- criar protótipo da tela inicial;
- definir regras de cancelamento;
- validar fluxo com possíveis usuários;
- revisar requisitos após feedback.

Para cada cartão, registrem:

- **título claro**;
- **breve descrição**;
- **por que o item é necessário**.

---

# 4. Priorização do Product Backlog

O Product Owner deverá conduzir a priorização dos cartões.

Organizem os itens considerando:

1. valor para o usuário;
2. importância para compreender o projeto;
3. dependências;
4. risco ou incerteza;
5. urgência.

Ao final, o Product Backlog deverá estar ordenado do item mais prioritário para o menos prioritário.

---

# 5. Definição das Sprints

Antes de distribuir os cartões entre as Sprints, o grupo deverá definir um **Sprint Goal** para cada uma.

O Sprint Goal deve indicar o resultado que o grupo deseja alcançar.

## Exemplo

**Sprint 1:** compreender os usuários e as regras centrais do problema.

**Sprint 2:** representar a solução através de requisitos e protótipos.

**Sprint 3:** validar e revisar a proposta do produto.

Criem um cartão para cada Sprint na lista **Sprint** e registrem nele:

- nome da Sprint;
- Sprint Goal;
- resultado esperado.

---

# 6. Planejamento das Sprints com Etiquetas

Agora os grupos deverão analisar os cartões do Product Backlog e indicar em qual Sprint pretendem trabalhar em cada item.

Utilizem as etiquetas:

- Sprint 1;
- Sprint 2;
- Sprint 3.

A pergunta principal é:

> **Em qual Sprint este trabalho deve ser realizado para contribuir com o Sprint Goal?**

Nem todos os cartões precisam receber uma Sprint imediatamente.

Itens que ainda não podem ser planejados podem permanecer sem etiqueta no Product Backlog.

---

# 7. Sprint Planning

Agora considere que a **Sprint 1 está prestes a começar**.

Analise todos os cartões que receberam a etiqueta **Sprint 1**.

O grupo deverá decidir quais desses itens realmente serão assumidos na Sprint.

Movam os itens selecionados:

**Product Backlog → Sprint Backlog**

Itens que não couberem na Sprint devem continuar no Product Backlog, mesmo que tenham inicialmente a etiqueta Sprint 1. Nesse caso, a equipe pode revisar a etiqueta e replanejá-los.

---

# 8. Refinamento dos Cartões da Sprint Backlog

Cada cartão selecionado para a Sprint deverá conter:

## Descrição

O que precisa ser realizado?

## Responsável

Quem ficará responsável por acompanhar o item?

Isso não significa que apenas essa pessoa poderá trabalhar nele.

## Critério de conclusão

Como o grupo saberá que o trabalho está pronto?

### Exemplo

**Cartão:** Identificar usuários do sistema

**Etiqueta:** Sprint 1

**Descrição:**  
Identificar todos os grupos que utilizarão ou serão afetados pelo produto.

**Critério de conclusão:**  
Lista com pelo menos três perfis de usuários e uma breve descrição de suas necessidades.

## Checklist

Quando necessário, dividam o cartão em pequenas tarefas.

### Exemplo

- identificar usuários diretos;
- identificar usuários indiretos;
- descrever necessidades;
- revisar com o grupo.

---

# 9. Análise de Capacidade

O grupo deverá olhar para a lista **Sprint Backlog** e responder:

> **Nós realmente conseguiríamos realizar tudo isso durante a Sprint?**

Se a resposta for não:

- devolvam itens ao Product Backlog;
- alterem a Sprint planejada por meio das etiquetas;
- dividam cartões muito grandes;
- revisem o Sprint Goal, caso necessário.

A Sprint deve representar aquilo que a equipe acredita ser possível concluir.

---

# 10. Simulação de Mudança

Considere a seguinte situação:

> **O cliente informa que uma necessidade considerada secundária pelo grupo é muito mais importante do que parecia inicialmente. Além disso, um item planejado para uma Sprint futura depende de uma informação que ainda não foi obtida.**

O grupo deverá decidir:

- qual cartão mudou de prioridade;
- se alguma etiqueta de Sprint precisa ser alterada;
- se algum item deve permanecer no Product Backlog por mais tempo;
- se o Sprint Goal continua válido.

Registrem as mudanças diretamente no Trello.
